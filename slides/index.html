O use case

Telemetria → perfil → recomendação

Corte didático: começamos na telemetria — a captura de screenshot (OCR/vision) fica fora. Super Mario World na demo; GTA VI no futuro.

Escopo

O que fica fora

  • Captura e análise de screenshot real (OCR/vision) — começamos nos eventos.
  • LLM no caminho determinístico — regras puras no motor.
  • UI/overlay — o sistema termina nas recomendações no console.
  • Non-goal explícito vale ouro: o que a spec não diz, o agente inventa.
Non-goals como slide: o escopo negativo é decisão de spec, não ausência de planejamento.

Homework

Adicione um novo jogo

no seu ritmo · individual

O copiloto hoje só conhece Super Mario World — o sistema precisa atender ao próximo jogo

  1. Escolha o jogo: Sonic, Zelda, o que você dominar.
  2. Especifique o que muda: eventos, perfis e a base de conhecimento por jogo.
  3. Projete com design patterns: o que vira interface/strategy, o que é específico de cada jogo.
  4. Rode o ciclo SDD completo — grill, spec, tickets e implement com TDD.

Critério de sucesso: o mesmo copiloto recomenda para dois jogos, sem duplicar o motor — a wiki já é organizada por jogo (openwiki/<game-slug>/).

A atividade amarra tudo: spec, design patterns na fronteira do domínio e a wiki multi-jogo.

Recapitulando

Cinco coisas para levar

  • A spec é o contrato que sobrevive à sessão.
  • O que você não diz, o agente inventa.
  • SDD serve para feature nova, arquitetura e agentes — o ciclo é o mesmo.
  • A base de conhecimento também tem spec: o schema da wiki.
  • O método transforma cada decisão em requisito testável.
